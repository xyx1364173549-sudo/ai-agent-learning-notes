# 2.5 分层记忆设计（工作记忆 / 情景记忆 / 语义记忆）· 详细版

> 本节是阶段二信息量最大的一章：**三层记忆 + SQLite 从零学起**。学完你要能回答三件事——为什么系统需要三层记忆而不是一层？数据是怎么存进数据库的？怎么让系统"知道下一步该推荐什么"？

---

## 一、总结

**一句话概括**：

> **三层记忆 = 工作记忆（滑动窗口，记得住"刚才说了啥"）+ 情景记忆（SQLite + 遗忘曲线，记得住"学过什么、忘没忘"）+ 语义记忆（知识图谱，知道"知识间谁先谁后、下一步该学啥"）。三件套合起来，就是毕业论文第 4 章"分层记忆"创新点的工程基座。**

### 为什么不能只有一层记忆？

| 只有一种记忆 | 会怎样 | 缺了什么 |
|---|---|---|
| 只记对话（工作记忆） | 重启即失忆，学过的全忘 | 持久化 |
| 只存记录（情景记忆） | 有流水账，但不知道知识点之间的先后关系 | 关系结构 |
| 只有图谱（语义记忆） | 知道知识结构，但不知道这个学生实际掌握多少 | 个人学情 |

三层互补，缺一不可。类比：**工作记忆 = 黑板（临时写，擦了就没了）；情景记忆 = 笔记本（写下来就长期保存，但只是流水账）；语义记忆 = 课程大纲（知识之间的先后顺序，告诉你先学啥后学啥）**。

### 三件套的数据流动（重要，答辩会问）

```
学生说话/答题
   │
   ▼
① 工作记忆（内存里）── 滑动窗口，只留最近 N 条 ──→ 发给大模型当上下文
   │
   │ 学完一个知识点，沉淀
   ▼
② 情景记忆（SQLite 表）── 存"学过什么、多难、几分、什么时候"──→ 检索时按遗忘曲线加权
   │
   │ 知识点之间的关系
   ▼
③ 语义记忆（SQLite 两表）── 存"知识点 + 掌握度"和"先修关系"──→ recommend_next 推荐下一步
```

## 二、对应知识点

### 2.5a 工作记忆：滑动窗口（`memory_working.py`）

#### 痛点（为什么需要它）

对话消息是无限增长的：用户每问一句、模型每答一句，就多两条消息。如果**每次都把全部历史**发给大模型：

- token 爆炸 → 费用飙升（LLM 按 token 计费）
- 上下文被无关历史淹没 → 模型"忘"了当前重点，回答质量下降
- 超过上下文窗口 → 直接报错

#### 方案：滑动窗口

只保留两类消息：

1. `system` 提示（角色设定，永远不能丢）
2. 最近的 N 条非 system 消息（N 就是"窗口大小"）

```python
def sliding_window(messages, max_turns):
    system = [m for m in messages if m["role"] == "system"]
    others = [m for m in messages if m["role"] != "system"]
    others = others[-max_turns:] if max_turns > 0 else []
    return system + others
```

#### 逐行拆解

| 行 | 代码 | 干了什么 |
|---|---|---|
| 2 | `system = [m for m in messages if m["role"] == "system"]` | 列表推导式：把 role 是 system 的消息全挑出来 |
| 3 | `others = [m for m in messages if m["role"] != "system"]` | 挑出非 system 的（对话消息） |
| 4 | `others[-max_turns:] if max_turns > 0 else []` | 取最后 max_turns 条；**max_turns=0 时返回空列表** |
| 5 | `return system + others` | 拼接：system 永远在最前面 |

#### 边界陷阱：`[-0:]`（本节第一坑，必考）

Python 切片里，`others[-0:]` 等价于 `others[0:]`——**返回整个列表**！

```python
others[-max_turns:] if max_turns > 0 else []   # ✅ max_turns=0 时返回 []
others[-max_turns:]                            # ❌ max_turns=0 时返回全部！
```

因为 `-0` 就是 `0`。所以窗口大小为 0 意味着"一条对话都不留"，必须显式钳制为 `[]`。

**类比**：教室黑板写满要擦掉旧的，只留最近几行板书。擦 0 行 = 把黑板全擦光，而不是"擦 0 行=啥也没擦"。

#### 边界测试（跑给你看）

| 场景 | 输入 | 期望 | 结果 |
|---|---|---|---|
| 正常 | max_turns=2 | system + 最近 2 条 | ✅ |
| 窗口为 0 | max_turns=0 | 只有 system | ✅（有钳制才对） |
| 负数 | max_turns=-1 | 逻辑上不该出现，保守返回空 | ✅ |
| 窗口超大 | max_turns=100 > 总条数 | 全部非 system 消息 | ✅（切片自动截断） |
| 无 system | 消息里没有 system | 只返回最近 N 条 | ✅ |

### 2.5b 情景记忆：SQLite + 遗忘曲线（`memory_episodic.py` + `memory_decay.py`）

#### 痛点

1. **要持久化**：学生学过的东西不能只存在对话里，程序重启就没了。
2. **"学过 ≠ 记住"**：时间越久忘得越多。检索时要按遗忘程度加权——最近学的权重高，很久以前学的权重低。

#### 方案 1：`episodes` 表持久化

SQLite 是**文件型数据库**——一个 `.db` 文件就是整个数据库，不需要装服务器，Python 自带 `sqlite3` 模块，零依赖。对单机应用（我们的学习伴侣）完全够用。

```sql
CREATE TABLE IF NOT EXISTS episodes (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,  -- 自增主键，每行唯一编号
    student_id TEXT NOT NULL,                      -- 哪个学生
    topic      TEXT NOT NULL,                      -- 学了什么知识点
    summary    TEXT NOT NULL,                      -- 内容摘要
    difficulty REAL NOT NULL,                      -- 难度（0~1）
    score      REAL NOT NULL,                      -- 掌握度得分
    started_at TEXT NOT NULL DEFAULT (datetime('now'))  -- 学习时间（ISO 字符串）
)
```

**为什么 `started_at` 用 TEXT？** SQLite 没有专门的日期类型，惯例是把时间存成 ISO 字符串（如 `"2026-09-02 21:30:00"`），Python 端用 `datetime.fromisoformat()` 解析。**注意：不是 `fromtimestamp()`**——那是给"秒数时间戳"用的，喂 ISO 字符串会类型报错（本节第二坑）。

#### save_episode：插入 + 拿回主键

```python
def save_episode(conn, student_id, topic, summary, difficulty, score):
    cur = conn.cursor()
    cur.execute("""
        INSERT INTO episodes (student_id, topic, summary, difficulty, score)
        VALUES (?, ?, ?, ?, ?)
    """, (student_id, topic, summary, difficulty, score))
    conn.commit()          # 提交事务，写入才真正落盘
    return cur.lastrowid   # 最后插入行的主键 id
```

**`lastrowid` 是什么（本节第三坑）**：

- `cur.lastrowid` = **最后插入那一行的主键 id 值**，不是"插了几条"
- 删掉数据后 id 不会回退（AUTOINCREMENT 只增不减）
- 计数要看 `cur.rowcount`（受影响的条数）或 `SELECT COUNT(*)`

```python
print(cur.lastrowid)   # 比如 3 —— 这行的主键是 3
# 不是"插了 3 条"！删过数据后 id 会有空洞
```

**踩坑实例**：`save_episode` 签名参数顺序和调用不一致 → 数据静默存反列（topic 和 summary 互换），不报错、查出来才发现。**函数参数顺序必须和 SQL 列顺序、调用传参顺序三处一致**，这是防"静默错"的铁律。

#### query_episodes：查询 + 排序

```python
def query_episodes(conn, student_id, limit):
    cur = conn.cursor()
    cur.execute("""
        SELECT id, started_at, topic, summary, score
        FROM episodes WHERE student_id = ?
        ORDER BY started_at DESC LIMIT ?
    """, (student_id, limit))
    return cur.fetchall()
```

**注意**：`ORDER BY started_at DESC` 按时间倒序（最新的在前）。**不写 ORDER BY 永远不要假设返回顺序**——数据库不保证（下面 2.5c 会演示 rowid 空洞）。

#### 方案 2：艾宾浩斯遗忘曲线加权

**原理**：记忆随时间指数衰减。距离学习时间越久，这条记忆在检索时的权重越低。

```python
import math
from datetime import datetime

def days_since(iso_str):
    """ISO 字符串 → 距离今天的天数"""
    dt = datetime.fromisoformat(iso_str)   # ✅ 不是 fromtimestamp！
    return (datetime.now() - dt).days

def decay_weight(days, lam):
    """遗忘曲线权重：w = e^(-λ·days)"""
    return math.exp(-lam * max(days, 0))   # days 取非负，防止未来时间算出 >1
```

**`math.exp(-x)` 是什么**：就是 `e` 的 `-x` 次幂，即 `e^(-x)`。**为什么是负数**？因为衰减曲线是"时间越久权重越低"——指数上的负号让函数值随 days 增大而从 1 单调下降到趋近 0。`exp(0)=1`（刚学完权重最大），`exp(-∞)→0`（远古记忆权重趋近 0）。

**`max(days, 0)` 是防什么**：如果时间数据出错（比如未来时间），days 是负数，`e^(正数) > 1` 会放大权重。钳到 0 保证权重永远在 (0, 1] 区间。

#### 检索排序：加权分 = 原始分 × 衰减权重

```python
def search_episodes(conn, student_id, limit, lam=0.03):
    cur = conn.cursor()
    cur.execute("""
        SELECT id, started_at, topic, summary, score
        FROM episodes WHERE student_id = ? ORDER BY started_at DESC
    """, (student_id,))
    rows = cur.fetchall()
    scores = []
    for r in rows:                                      # 每一条都要算 → 循环内
        id_, started_at, topic, summary, score = r      # 元组解包：一行拆成 5 个变量
        days = days_since(started_at)
        weight = decay_weight(days, lam)
        scores.append((score * weight, id_, topic, days, weight))  # append 在循环内！
    scores.sort(reverse=True)                           # 全部算完才排一次 → 循环外！
    return scores[:limit]
```

**本节第四坑（缩进）**：`append` 必须在循环**内**（每一条都要收集），`sort`/`return` 必须在循环**外**（全部处理完才排一次）。放错层的后果：append 出循环 → 只剩最后一条；sort 进循环 → 每次排序只对当前一条。

**元组解包**：`id_, started_at, topic, summary, score = r` 把一行元组 `(1, "2026-...", "二次方程", "...", 0.6)` 按顺序拆给 5 个变量。**变量个数必须和列数一致**，多一个少一个都报 `ValueError`。

#### λ 翻转实验（论文第 7 章实验素材）

λ 控制遗忘速度：**λ 越大忘得越快**（更看重近期），**λ 越小越"重实力"**（原始得分主导）。

| λ | 二次方程（60 天前，原始 60） | 函数图像（38 天前，原始 38） | 加权后排序 |
|---|---|---|---|
| 0.03 | 60 × e^(-0.03×60) = 60×0.165 ≈ 9.9 | 38 × e^(-0.03×38) = 38×0.319 ≈ 12.1 | 二次方程 ＞ 函数图像（因为 60 分底子厚） |
| 0.01 | 60 × e^(-0.01×60) = 60×0.549 ≈ 32.9 | 38 × e^(-0.01×38) = 38×0.684 ≈ 26.0 | **函数图像 ＞ 二次方程**（时间差距不敏感，比原始分） |

**翻转的含义**：同一个数据库、同一个查询，只调 λ 就得到相反的排序结果。这说明"遗忘参数"直接决定检索偏好——调到 0.03 会优先捞"更久前但更扎实"的记忆，调到 0.01 会优先捞"更近期"的记忆。写论文时这一张表就能当实验数据。

### 2.5c 语义记忆：知识图谱（两张表降级实现，`memory_semantic.py`）

#### 痛点

情景记忆只能回答"学过什么"，回答不了"**接下来该学什么**"。因为系统不知道知识点之间的先后关系——先学因式分解，才能学二次方程；先学二次方程，才能学函数图像。

#### 方案：一张"图" = 两张表

真正的知识图谱通常用图数据库（Neo4j）实现。我们用 SQLite 降级实现：**"点"一张表，"边"一张表**——避开学图数据库，降低毕设难度，功能照样够。

**类比**：`knowledge` 是**地铁站**（站点本身 + 人流量），`prerequisites` 是**线路图上的连线**（哪站到哪站）。地铁图少了任何一张都不成立。

```sql
-- 点表：每个知识点 + 每个学生的掌握度
CREATE TABLE IF NOT EXISTS knowledge (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    student_id TEXT NOT NULL,
    topic      TEXT NOT NULL,
    mastery    REAL DEFAULT 0.0,
    UNIQUE(student_id, topic)        -- 同一学生同一知识点只能有一条
)

-- 边表：先修关系 from_topic → to_topic
CREATE TABLE IF NOT EXISTS prerequisites (
    from_topic TEXT NOT NULL,        -- 先修知识点
    to_topic   TEXT NOT NULL,        -- 目标知识点
    PRIMARY KEY (from_topic, to_topic)   -- 同一条边不能重复
)
```

**UNIQUE 和 PRIMARY KEY 的区别**：主键（PRIMARY KEY）一表只能有一个，且不能为空；UNIQUE 约束可以有好几个，允许空值。这里点表用 `UNIQUE(student_id, topic)`（组合唯一：同学生同知识点唯一），边表用组合主键 `(from_topic, to_topic)`（同一条边唯一）。**这两处约束就是 upsert 能工作的前提**——没有唯一约束，重复插入不会报错，upsert 也就没有"冲突"可处理。

#### 写数据：upsert 两兄弟

**① `ON CONFLICT ... DO UPDATE`（点表用，撞了要改）**

```sql
INSERT INTO knowledge (student_id, topic, mastery) VALUES (?, ?, ?)
ON CONFLICT (student_id, topic)           -- 撞到唯一键了？
DO UPDATE SET mastery = excluded.mastery  -- 用新值把旧掌握度盖掉
```

- `ON CONFLICT (student_id, topic)`：声明"冲突发生在哪把锁上"
- `excluded`：SQLite 关键字，指**那个想插进来、但被唯一键拦下的新行**。`excluded.mastery` = 新传进来的掌握度
- 整套动作 = **upsert**（update + insert）：有就改，没有就加

**类比**：期末考完登记成绩单。学号+科目已经有了一行 → 不新增行，只把分数**更新**成新成绩；没有 → 新写一行。**没有 `ON CONFLICT` 这一句**，第二次对同一个 `(student_id, topic)` 执行 INSERT 会直接抛 `IntegrityError: UNIQUE constraint failed`。

**② `INSERT OR IGNORE`（边表用，撞了就算了）**

```sql
INSERT OR IGNORE INTO prerequisites (from_topic, to_topic) VALUES (?, ?)
```

同样撞主键，态度完全不同：**直接跳过，不报错，也不覆盖**。"因式分解→二次方程"这条边加两次，语义上就是同一条边，多写没意义。

**一句话区分**：**成绩单撞了要更新（DO UPDATE），关系表撞了就忽略（OR IGNORE）。**

#### 读数据：fetch 三形态

| 方法 | 返回什么 | 没有数据时 | 什么时候用 |
|---|---|---|---|
| `fetchone()` | **单个元组** `("二次方程", 0.6)` | `None` | `get_mastery` 查单个掌握度 |
| `fetchall()` | **元组组成的列表** `[("因式分解",0.9), ...]` | `[]` | 查一批知识点 / 先修 |
| `fetchmany(n)` | 元组列表，最多 n 条 | `[]` | 分页（现在用不到） |

**关键认知：数据库返回的每一行永远是元组，哪怕只有一个字段。**

```python
cur.fetchall()  →  [("因式分解",), ("全等三角形",)]   # 每行是单元素元组
[r[0] for r in ...]  →  ["因式分解", "全等三角形"]      # 剥掉元组壳，只要字符串
```

#### 为什么数据库给你元组而不是列表？

1. **数据库行是不可改的快照**。给你列表你就能 `row[0] = 0.0` 手滑改掉，但改的只是 Python 里的拷贝，数据库纹丝不动——产生"我明明改了怎么没变"的错觉。元组想改都改不了，逼你想改就必须走 SQL（`UPDATE`）。
2. **元组可以当字典的 key**。列表可变、不能哈希、不能当 key；元组可以。以后写缓存、写去重，元组直接塞 `set`/`dict` 都没问题。

#### `r[0]` 是列下标，不是行下标（本节最重要的认知纠偏）

```python
pres = [r[0] for r in cur.fetchall()]
```

- **行下标** = "现在是第几行"——不用你写，`for r in rows` 每次循环**自动换一行**
- **列下标** = "取这一行的第几个字段"——`r[0]` 固定取**第 0 列**，不管 r 现在是哪一行

读作：**"每一行 r，都取它的第 0 列"**。三行数据 → 三个 `r[0]` → 三个字符串。看起来"一样"，是因为语法一样，不是取的同一条。

**类比**：全班点名，老师喊"报一下你们的学号"——每个被点到的人（r 依次是第 1 个、第 2 个……）报的都是"学号"（第 0 列），你不会觉得老师只问了第一个人。

**列数由 SELECT 决定**：`SELECT topic, mastery` → 每行 2 个元素，`r[0]`=topic、`r[1]`=mastery；`SELECT from_topic` → 每行 1 个元素，`r[0]` 就是唯一元素。**跟 WHERE 无关，WHERE 只是筛行，不会加列。**

#### 数据库返回顺序不保证（附现场演示）

实测：先插甲（rowid=1）、乙（2）、丙（3），删掉乙，再插丁——

```
第一次查询:  甲(1) 乙(2) 丙(3)     ← 碰巧按插入顺序
删乙、再插丁: 甲(1) 丙(3) 丁(4)     ← 2 号位空了，丁没有补进来
```

删掉的乙那个位置（2）就**空着**，新插的丁拿到 rowid=4。数据库只保证每行有唯一编号，**不保证返回顺序像数组一样连续**。

> **铁律：不写 `ORDER BY`，就永远不要假设返回顺序。**

所以 `recommend_next` 里取"掌握度最低"时要**自己 sort**：

```python
candidates.sort()        # 排序是你要自己做的，数据库不帮你排
return candidates[0][1]  # sort 之后才是真的"最弱的"
```

#### 核心算法：`recommend_next` 两关判定——"够得着的最差的"

```python
def recommend_next(conn, student_id):
    cur = conn.cursor()
    cur.execute("SELECT topic, mastery FROM knowledge WHERE student_id = ?", (student_id,))
    rows = cur.fetchall()          # ① 先把"所有知识点"端回 Python 存好
    candidates = []                # 空篮子：装"够得着"的候选
    for topic, mastery in rows:
        if mastery >= 0.7:
            continue               # 第一关：已掌握 → 跳过
        # 第二关：查这个知识点的所有先修（查的是边表，跟掌握度无关）
        cur.execute(
            "SELECT from_topic FROM prerequisites WHERE to_topic = ?",
            (topic,),
        )
        pres = [r[0] for r in cur.fetchall()]   # 剥壳：元组列表 → 字符串列表
        ready = True               # 乐观假设：先假设够得着
        for p in pres:             # 逐个先修把关
            if get_mastery(conn, student_id, p) < 0.7:
                ready = False      # 有一个先修没学会 → 否掉
                break
        if ready:                  # 两关都过 → 收进篮子（必须与 for p 平级！）
            candidates.append((mastery, topic))
    if not candidates:
        return None                # 没有候选
    candidates.sort()              # 掌握度升序（弱 → 强）
    return candidates[0][1]        # 返回最弱的那个
```

**三层结构口诀（本节第四坑的升级版）**：

```
for topic, mastery in rows:      ← 第 1 层：每条知识点都要做
    if mastery >= 0.7: continue  ←   判定1：已掌握的跳过
    pres = ...                   ←   查这个知识点的先修
    ready = True                 ←   乐观假设
    for p in pres:               ← 第 2 层：一个知识点的先修逐个查
        if ... < 0.7:            ←   判定2：有先修没学会
            ready = False
            break
    if ready:                    ← 回到第 1 层 ← 必须和 for p 平级！
        candidates.append(...)
if not candidates: return None   ← 第 3 层：全部处理完才收尾
candidates.sort()
return candidates[0][1]
```

- **每条知识点都要做的 → 第 1 层**
- **一个知识点的先修逐个查 → 第 2 层**
- **全部弄完才做一次 → 第 3 层**

**踩过的两个具体错法**：
1. `for` 循环体只剩 `continue`，后面的 `cur.execute` 掉到循环外 → 循环空转三圈，`topic` 残留最后一个值"函数图像"，查出先修"二次方程"掌握度 0.6<0.7 → `ready=False` → 返回 `None`。**不报错，静默跑错，最阴险。**
2. `if ready:` 缩进在 `for p` 里面 → 每个先修达标后都 append 一次。多先修场景下（如"三角函数"依赖"相似三角形"+"全等三角形"）同一个知识点被收集两次。**当前数据只有一个先修看不出来，真实图谱里三四个先修是常态——本地全绿、上线才炸。**

#### 完整走查（测试数据逐步推演）

```
知识点表（stu001）：
  因式分解 0.9  |  二次方程 0.6  |  函数图像 0.3
边表：
  因式分解 → 二次方程  （先学因式分解才能学二次方程）
  二次方程 → 函数图像  （先学二次方程才能学函数图像）
```

| 知识点 | 第一关（掌握≥0.7？） | 第二关（先修全达标？） | 结果 |
|---|---|---|---|
| 因式分解 | 0.9 ≥ 0.7 → **跳过** | 根本没机会查 | 不候选 |
| 二次方程 | 0.6 < 0.7 → 过关 | 先修=因式分解，get_mastery=0.9 ≥ 0.7 ✅ | **候选 (0.6, 二次方程)** |
| 函数图像 | 0.3 < 0.7 → 过关 | 先修=二次方程，get_mastery=0.6 < 0.7 ❌ → 淘汰 | 不候选 |

`candidates = [(0.6, "二次方程")]` → sort → 返回 `"二次方程"`。

**为什么不是掌握度最低的"函数图像"（0.3）？** 因为函数图像的先修"二次方程"只有 0.6，还没学会。硬推函数图像等于把学生往墙上撞——学不会。系统推荐的是"**够得着的最差的**"：先修全达标里，挑掌握度最低的，保证"推了就能学会"。

### 贯穿知识点：SQLite 基础（数据库四件套）

这节从零学了 SQLite，把最关键的知识点集中在这里。

#### 四件套：conn / cursor / execute / fetch

**类比：去图书馆查资料。**

| 代码 | 图书馆类比 | 干什么 |
|---|---|---|
| `conn = sqlite3.connect(...)` | 办了张借书证 | 建立一条到数据库文件的连接通道 |
| `cur = conn.cursor()` | 叫了个管理员帮你跑腿 | 真正执行 SQL 的"手" |
| `cur.execute(SQL, 参数)` | 把书单递给管理员 | 让他跑一趟，把结果**暂时端在手上** |
| `cur.fetchall()` | 你把书从管理员手里接过来 | 把结果**拿回 Python**，变成列表 |

**游标是"独臂服务员"——一次只能端一盘菜**：你 `execute` 第二次，第一盘结果就被自动收走了。所以嵌套查询时必须先 `fetchall()` 固化：

```python
rows = cur.fetchall()   # ← 先把"所有知识点"端走存好
# 之后再 execute 查先修，就不会弄丢 rows
```

**不存、直接 `for t, m in cur:` 迭代游标**：循环里再次 `execute` 时，游标手上那盘菜被换掉，外层循环直接乱套。**先 fetchall 固化成列表，再进循环**——SQL 嵌套查询的通用铁律。

#### `?` 占位符：为什么不用 f-string？

```python
# 千万别这么写（f-string 拼接 SQL）
f"SELECT ... WHERE student_id = '{student_id}'"

# 要这么写（占位符）
cur.execute("SELECT ... WHERE student_id = ?", (student_id,))
```

三个原因：
1. **防 SQL 注入**：用户输入被当纯数据处理，永远不会被当成 SQL 执行
2. **自动处理引号转义**：中文、标点、引号都不会把 SQL 撑爆
3. **数据库能缓存执行计划**：同一条 SQL 反复执行更快

#### `(student_id,)` 尾巴那个逗号不能省

```python
cur.execute("... WHERE student_id = ?", (student_id,))
#                                           ↑ 这个逗号
```

参数第二项必须是**元组**。`(student_id)` 只是加了括号的字符串，不是元组；`(student_id,)` 才是。单元素元组的逗号是 Python 经典暗坑——**和 `("因式分解",)` 单列查询结果是同一个规矩**。

#### 事务：`conn.commit()`

SQLite 默认开启事务。`execute` 只改了内存里的暂存，**`commit()` 才真正写入文件**。忘记 commit 的后果：程序正常结束（连接关闭时自动回滚），数据"看起来写了"实际没落盘。

#### 进阶（先记着，毕业设计用得上）

```python
conn.row_factory = sqlite3.Row   # 之后 row["topic"] 直接按列名取值
```

给连接配一个"翻译官"，让每行从元组变成能按列名取的字典式对象，不用记"第 0 列是 topic 还是 mastery"。当前代码用 `r[0]` 完全没问题，这是"以后让代码更可读"的优化项。

"""2.5a 工作记忆：滑动窗口"""
def sliding_window(messages, max_turns):
    """保留 system 提示 + 最近 max_turns 条非 system 消息"""
    system = [m for m in messages if m["role"] == "system"]
    others = [m for m in messages if m["role"] != "system"]
    others = others[-max_turns:] if max_turns > 0 else []  # 防 [-0:] 返回全列表
    return system + others

# 测试
msgs = [
    {"role": "system", "content": "你是数学导师"},
    {"role": "user", "content": "什么是因式分解？"},
    {"role": "assistant", "content": "把一个多项式拆成几个整式相乘"},
    {"role": "user", "content": "举例说明"},

]
print(sliding_window(msgs, 2))   # system + 最近 2 条
print(sliding_window(msgs, 0))   # 只有 system，不是全部！
print(sliding_window(msgs, 100)) # 窗口大于总数 → 全部非 system

            summary    TEXT NOT NULL,
            difficulty REAL NOT NULL,
            score      REAL NOT NULL,
            started_at TEXT NOT NULL DEFAULT (datetime('now'))

def save_episode(conn, student_id, topic, summary, difficulty, score):
    cur = conn.cursor()
    cur.execute("""
        INSERT INTO episodes (student_id, topic, summary, difficulty, score)
        VALUES (?, ?, ?, ?, ?)
    """, (student_id, topic, summary, difficulty, score))
    conn.commit()
    return cur.lastrowid  # 最后插入行的主键 id，不是"插了几条"！

    cur.execute("""
        SELECT id, started_at, topic, summary, score
        FROM episodes WHERE student_id = ?
        ORDER BY started_at DESC LIMIT ?
    """, (student_id, limit))
    return cur.fetchall()

### 3.3 情景记忆：遗忘曲线加权（`memory_decay.py`）

```python
"""2.5b 情景记忆：艾宾浩斯时间衰减检索"""
import sqlite3, math
from datetime import datetime

def days_since(iso_str):
    """ISO 字符串 → 距离今天的天数"""
    dt = datetime.fromisoformat(iso_str)   # 不是 fromtimestamp！
    return (datetime.now() - dt).days

def decay_weight(days, lam):
    """遗忘曲线权重：w = e^(-λ·days)，days 取非负"""
    return math.exp(-lam * max(days, 0))

def search_episodes(conn, student_id, limit, lam=0.03):
    cur = conn.cursor()
    cur.execute("""
        SELECT id, started_at, topic, summary, score
        FROM episodes WHERE student_id = ? ORDER BY started_at DESC
    """, (student_id,))
    rows = cur.fetchall()
    scores = []
    for r in rows:                      # 每一条都要做 → 循环内
        id_, started_at, topic, summary, score = r   # 元组解包
        days = days_since(started_at)
        weight = decay_weight(days, lam)
        scores.append((score * weight, id_, topic, days, weight))
    scores.sort(reverse=True)           # 全部做完才做 → 循环外
    return scores[:limit]
```

### 3.4 语义记忆：知识图谱（`memory_semantic.py`）

```python
"""2.5c 语义记忆：知识图谱（简化版：两张表）"""
import sqlite3

DB_PATH = "memory.db"

def init_db(db_path=DB_PATH):
    conn = sqlite3.connect(db_path)
    cur = conn.cursor()
    cur.execute("""
        CREATE TABLE IF NOT EXISTS knowledge (
            id         INTEGER PRIMARY KEY AUTOINCREMENT,
            student_id TEXT NOT NULL,
            topic      TEXT NOT NULL,
            mastery    REAL DEFAULT 0.0,
            UNIQUE(student_id, topic)
        )
    """)
    cur.execute("""
        CREATE TABLE IF NOT EXISTS prerequisites (
            from_topic TEXT NOT NULL,
            to_topic   TEXT NOT NULL,
            PRIMARY KEY (from_topic, to_topic)
        )
    """)
    conn.commit()
    return conn

def update_mastery(conn, student_id, topic, mastery):
    """更新（或新建）掌握度：撞了唯一键就盖新值（upsert）"""
    cur = conn.cursor()
    cur.execute("""
        INSERT INTO knowledge (student_id, topic, mastery)
        VALUES (?, ?, ?)
        ON CONFLICT (student_id, topic)
        DO UPDATE SET mastery = excluded.mastery
    """, (student_id, topic, mastery))
    conn.commit()

def add_prerequisite(conn, from_topic, to_topic):
    """记录先修关系：撞了主键就跳过（不重复加边）"""
    cur = conn.cursor()
    cur.execute(
        "INSERT OR IGNORE INTO prerequisites (from_topic, to_topic) VALUES (?, ?)",
        (from_topic, to_topic),
    )
    conn.commit()

def get_mastery(conn, student_id, topic):
    """查掌握度；没学过返回 0.0"""
    cur = conn.cursor()
    cur.execute(
        "SELECT mastery FROM knowledge WHERE student_id = ? AND topic = ?",
        (student_id, topic),
    )
    row = cur.fetchone()
    return row[0] if row else 0.0

def recommend_next(conn, student_id):
    """推荐"够得着的最差的"：掌握度<0.7 且所有先修>=0.7 中掌握度最低者"""
    cur = conn.cursor()
    cur.execute("SELECT topic, mastery FROM knowledge WHERE student_id = ?", (student_id,))
    rows = cur.fetchall()
    candidates = []
    for topic, mastery in rows:
        if mastery >= 0.7:
            continue                 # 第一关：已掌握 → 跳过
        cur.execute(
            "SELECT from_topic FROM prerequisites WHERE to_topic = ?",
            (topic,),
        )
        pres = [r[0] for r in cur.fetchall()]
        ready = True                 # 乐观假设
        for p in pres:               # 第二关：逐个先修把关
            if get_mastery(conn, student_id, p) < 0.7:
                ready = False
                break
        if ready:                    # 与 for p 平级！
            candidates.append((mastery, topic))
    if not candidates:
        return None
    candidates.sort()                # 掌握度升序
    return candidates[0][1]          # 返回最弱的那个

# 测试
if __name__ == "__main__":
    conn = init_db()
    update_mastery(conn, "stu001", "因式分解", 0.9)
    update_mastery(conn, "stu001", "二次方程", 0.6)
    update_mastery(conn, "stu001", "函数图像", 0.3)
    add_prerequisite(conn, "因式分解", "二次方程")
    add_prerequisite(conn, "二次方程", "函数图像")
    print("二次方程掌握度:", get_mastery(conn, "stu001", "二次方程"))  # 0.6
    print("没学过的:     ", get_mastery(conn, "stu001", "勾股定理"))  # 0.0
    print("推荐下一个:   ", recommend_next(conn, "stu001"))           # 二次方程
    conn.close()
```

## 四、本节踩坑清单（汇总，复习必看）

| # | 坑 | 表现 | 根治 |
|---|---|---|---|
| 1 | `[-0:]` 切片 | `max_turns=0` 返回整个列表 | `if max_turns > 0 else []` |
| 2 | `fromtimestamp(ISO字符串)` | 类型报错 | 用 `fromisoformat` |
| 3 | `lastrowid` 当"插入条数" | 误以为返回 2 条 | 它是最后插入行的主键 id；计数用 `rowcount`/`COUNT(*)` |
| 4 | 循环缩进（两次） | 静默跑错/只剩一条 | append 循环内，sort/return 循环外 |
| 5 | `if ready:` 缩进进 `for p` | 多先修时重复收集 | 与 `for p` 平级 |
| 6 | 列名/占位符数量不匹配 | `4 values for 3 columns` 崩溃 | 改列名时同步数 VALUES 的 `?` |
| 7 | 函数参数顺序不一致 | 数据静默存反列 | 签名/SQL 列/调用三处对齐 |
| 8 | 忘 `commit()` | 数据没落盘 | 改完必 commit |
