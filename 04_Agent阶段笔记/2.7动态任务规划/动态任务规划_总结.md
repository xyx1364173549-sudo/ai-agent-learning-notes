# 2.7 动态任务规划（Plan-and-Execute）· 详细版

> 本节是阶段二的"承上启下之章"：把 2.5c 的知识图谱（memory.db）和 2.6 的四 Agent 流水线**焊在一起**，让学习路径不再写死在提示词里，而是由图谱状态实时"长"出来。学完你要能回答三件事——2.6 的规划"假"在哪？2.7 靠什么让它变"真"？"下一个学什么"到底是谁在什么时候决定的？

---

## 一、总结

**一句话概括**：

> **动态任务规划 = 把 2.5c 的知识图谱变成"规划引擎"：每学完一个知识点（eval 判 ≥0.7），plan_node 就把掌握度写回图谱，再问 `recommend_next()` 现算下一站；图谱没候选就发 `done` 真正结束。路径不是任何人写死的，是"地图（图谱）+ 进度（掌握度）"在运行时算出来的。**

### 痛点：2.6 的规划是"假规划"

| 对比 | 2.6 的规划 | 2.7 的规划 |
|---|---|---|
| 依据 | prompt 里写死的**直线名单**（因式分解→二次方程→函数图像→勾股定理） | 图谱里的**点和边**（谁是谁的先修） |
| 谁来算 | LLM 照着名单"背" | `recommend_next()` 确定性计算 |
| 结果 | 谁走都一样，换学生不换路 | 掌握度一变，候选跟着变，**每个人走出自己的路** |
| 可靠性 | 模型可能乱说 | 纯代码，可解释、可测试、可写进论文 |

**类比**：2.6 像旅行团发的"固定行程单"（几点到哪都印好了）；2.7 像给你一张**地图 + 导航**——你从广州出发（起点），每过一座城考你一次，导航根据"你现在在哪、路通没通"现场规划下一站。**行程单 vs 地图 + 导航，这就是静态与动态的本质。**

### 范式：Plan-and-Execute（规划-执行）

2.6 是 **ReAct 式**（走一步看一步）；2.7 是业界任务型 Agent 的标准架构：

```
Planner(规划器) → 生成/调整任务清单
     ↓
Executor(执行器) → 按清单一步步执行(tutor → quiz → eval)
     ↓
Re-planner(重规划器) → 每执行一步,根据结果回头调整计划
     ↓ 循环……
```

**规划不是一次性做完，是边走边动态调整——"动态"两个字就来自这里。**

### 本节最关键的顿悟：2.5c 的 `recommend_next` 就是现成的规划引擎

当时你可能觉得它只是个练习题——**现在它的身份揭晓了**：掌握度 < 0.7、且先修全 ≥ 0.7 的知识点里挑最弱的，"推荐**够得着的最差的**"。这正是规划 Agent 的大脑。

## 二、对应知识点

### 2.7.1 从 2.6 到 2.7：三个缺口 → 三个升级

| 2.6 的缺口 | 后果 | 2.7 的补法 |
|---|---|---|
| 规划不"看"学生状态（没写回） | 系统是"瞎子"，不知道学生学得咋样 | plan_node 先 `update_mastery` **写回图谱** |
| 规划靠 LLM 背名单（没问图谱） | 系统是"笨的"，路径千人一面 | 问 `recommend_next()` **图谱推荐** |
| plan 输出"无"图却不停 | 学完了还白烧一轮 | 无候选 → `{"action": "done"}` **真结束** |

### 2.7.2 图结构（对比 2.6 的一处关键改动）

```
START → tutor → quiz → eval ─┬─ mastery≥0.7 → plan ─┬─ 有候选 → tutor(讲新课)
                              └─ mastery<0.7  → tutor ┘  └─ 无候选 → END(学完了)
                                              (回炉巩固)     (真正的结束信号!)
```

**改动：2.6 是 `plan → quiz`（绕过导师），2.7 改成 `plan → tutor`。** 讲新课当然要先讲课再出题——这一改，导师成了所有路径的**必经节点**，2.6 那个"plan 回边绕过 tutor 导致 round 冻结"的死循环隐患**从结构上消失了**（保险丝还在，但成了纯保险）。

### 2.7.3 plan_node：本节核心升级（三步走）

```python
def plan_node(state: AgentState) -> dict:
    conn = init_db(DB_PATH)
    # ① 写回:把这次评估的掌握度存进图谱(让地图上的进度是最新的)
    update_mastery(conn, STUDENT, state.get("topic"), state.get("mastery", 0))
    # ② 问图谱:现在"够得着的最差的"是谁?
    nxt = recommend_next(conn, STUDENT)
    conn.close()
    # ③ 决策:有候选 → 推进(换 topic);无候选 → done
    if nxt is None:
        return {"action": "done"}              # 真正的 END!
    return {"action": "next", "topic": nxt}    # 接力棒交给新知识点
```

注意第 ③ 步**只动 action 和 topic**——topic 换了，下一轮导师才讲新课；mastery / round / question 都不能碰。

### 2.7.4 闭环逐站走查（谁写谁读）

| 站 | 节点 | 干什么 | 状态变化 |
|---|---|---|---|
| 1 | tutor | 讲当前知识点 | — |
| 2 | quiz | 考当前知识点（外部指定题则沿用） | `question` |
| 3 | eval | 批改，出掌握度（三层兜底） | `mastery` + `round` |
| 4 | should_continue | `mastery≥0.7`？ | 是→plan；否→回 tutor 重讲 |
| 5 | **plan** ⭐ | ① 写回图谱 ② 问 `recommend_next` | 图谱掌握度更新 |
| 6 | plan_decision | `action=="done"`？ | done→END；next→回 tutor 讲新课 |

### 2.7.5 谁在什么时候决定下一个知识点（验收核心概念）

| 角色 | 是谁 | 决定什么 | 什么时候起作用 |
|---|---|---|---|
| **规则** | 你（setup_student 建图） | 谁有**资格**当候选（先修门槛） | **静态**，一直存在，不是某个时刻 |
| **状态** | 测试（每轮答案→掌握度） | 学到**哪了**（进度） | 运行时不断变化 |
| **人选** | `recommend_next` 算法 | 够得着的里面**具体选谁** | **每次 eval≥0.7 踏进 plan 的那一瞬间** |

> 一句话钉死：**你能定义"游戏规则"（图谱）和"玩家表现"（答案），但"下一步推荐谁"是裁判（算法）在每次回合结束后按规则 + 表现现判的——你无法钦定，只能影响。** 改一个答案数字，掌握度变，下次过关后推荐就跟着变——这就是"动态"。

### 2.7.6 防死循环：结构修复为主，保险丝兜底

- **结构修复**：`plan → tutor` 让 tutor 成为必经节点，2.6 的路径枚举隐患消失
- **保险丝**：`should_continue` 里 `round >= 10 → end`（正常不会触发，纯保险）
- **语义**：`round` 每 eval 一次 +1，= "学了几轮"

### 2.7.7 遗留问题（2.8 论文系统再解）

`quiz_node` 沿用外部传入的 question，导致推进到新知识点后出现"topic=函数图像、考题却是二次方程的题"的错配。真实系统应在 topic 变更时清空 question 重新出题，或每个知识点绑定固定题库。当前演示没崩，先记着。

## 三、测试验收

### 主场景（真实 LLM，修正答案后）

```
=== 场景 1: 学二次方程(答对) ===
最终掌握度: 0.7         ← 最后一轮(函数图像)的评估
plan 决策:  done         ← 全学完了!真正的结束信号!
当前知识点: 函数图像     ← 中间发生了 next(二次方程→函数图像)推进
图谱中二次方程掌握度: 1.0 ← 写回成功!
```

### 教学宝藏：一次"答错"其实是代码正确的铁证

测试答案笔误 `x=0`（应为 x=2）→ eval 判 0.4 → 回炉 → 同一份错答案永远 0.4 → round≥10 收工。**这不是 bug，恰恰验证了三件事**：① should_continue 判定正确（0.4<0.7 走 retry）；② 保险丝防死循环生效；③ 没到 plan 就不写回，图谱 0.0 未被污染——系统正确识别"没学会"并拒绝推进。

### 桩版边界测试（不烧 LLM，替换 llm 为桩）16/16 全过

| 场景 | 输入 | 断言 | 结果 |
|---|---|---|---|
| 1 沿链学完 | 二次方程答对 | action=done / topic=函数图像 / tutor 2 次 / eval 2 次 / 两知识点写回 ≥0.7 | ✅ |
| 5 全学会再跑 | 起点函数图像答对 | 一轮就 done，eval 只 1 次 | ✅ |
| 2 一直答错 | 答案"不会" | 保险丝 10 轮收场（eval/tutor 各 10 次）、topic 没变、图谱没被写回（0.0） | ✅ |
| 3 多分支 | X0.9/Y0.4/C0.2，C 依赖 X+Y | 推荐 **Y**（C 被先修 Y 卡住；Y 无门槛够得着） | ✅ |
| 4 学生隔离 | stu003 与 stu002 同库 | stu003.C 保持 0.2、无"函数图像"记录（不串数据） | ✅ |

## 四、本节踩坑清单

| # | 坑 | 表现 | 根治 |
|---|---|---|---|
| 1 | 概念：以为"2.7 路径是测试时写的" | 复述验收题答偏 | 路径是运行时 `recommend_next` 现算的；setup_student 只布置棋盘（规则），invoke 只给起点和表现 |

## 五、论文定位（答辩话术）

- **第 5 章"动态任务规划"的核心立论**：路径调整是**基于知识图谱状态的确定性计算**（`recommend_next`），不是模型随机发挥——"我的路径是'地图 × 进度'算出来的，可解释、可测试"。
- **创新点表述**：不是推荐"掌握度最低的"，而是推荐"**够得着的最差的**"（先修全达标里最弱的）——`recommend_next` 的两关判定 + 图谱边表就是抓手。
- **对比实验素材**：同一份代码，改一个答案数字走出两条完全不同的路（答错回炉 vs 答对推进到 done）——动态性的实证。
- **遗留问题也是加分项**：quiz 题库错配问题，论文第 5 章可以写"知识点-题库绑定"作为改进方向。
