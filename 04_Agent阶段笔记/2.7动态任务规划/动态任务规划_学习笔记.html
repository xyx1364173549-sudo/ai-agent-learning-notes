2.7 动态任务规划（Plan-and-Execute）

把 2.5c 知识图谱焊进 2.6 四 Agent 流水线 → 路径由图谱状态实时"长"出来 → 论文第 5 章核心
动态任务规划 = 每学完一个知识点（eval 判 ≥0.7），plan_node 就把掌握度写回图谱，再问 recommend_next() 现算下一站；图谱没候选就发 done 真正结束。路径不是任何人写死的，是"地图（图谱）+ 进度（掌握度）"在运行时算出来的。

一、痛点：2.6 的规划是"假规划"

对比2.6 的规划2.7 的规划
依据prompt 里写死的直线名单图谱里的点和边（先修关系）
谁来算LLM 照着名单"背"recommend_next() 确定性计算
结果谁走都一样，换学生不换路掌握度一变候选就变，每个人走出自己的路
可靠性模型可能乱说纯代码，可解释、可测试、可写进论文

类比：2.6 像旅行团发"固定行程单"；2.7 像给你一张 地图 + 导航——你从广州出发（起点），每过一座城考你一次，导航根据"你现在在哪、路通没通"现场规划下一站。行程单 vs 地图+导航，就是静态与动态的本质。

二、范式：Plan-and-Execute（规划-执行）

2.6 是 ReAct 式（走一步看一步）；2.7 换成业界任务型 Agent 的标准架构——规划不是一次性做完，是边走边动态调整，"动态"两个字就来自这里。

1
Planner 规划器
生成 / 调整任务清单
2
Executor 执行器
按清单执行 tutor→quiz→eval
3
Re-planner 重规划器
每执行一步，按结果回头调计划
4
循环
直到图谱无候选 → done
本节最关键的顿悟：2.5c 的 recommend_next 当时只是个练习题——现在它的身份揭晓了：它就是规划 Agent 的大脑。"推荐够得着的最差的"（掌握度<0.7 且先修全≥0.7 里挑最弱）正是动态规划的核心。

三、从 2.6 到 2.7：三个缺口 → 三个升级

2.6 的缺口后果2.7 的补法
规划不"看"学生状态系统是"瞎子"plan_node 先 update_mastery 写回图谱
规划靠 LLM 背名单系统是"笨的"，路径千人一面问 recommend_next() 图谱推荐
plan 输出"无"图却不停学完了还白烧一轮无候选 → done 真正的结束

四、图结构 + plan_node（本节核心）

START → tutor → quiz → eval ─┬─ mastery≥0.7 → plan ─┬─ 有候选 → tutor(讲新课)
                              └─ mastery<0.7  → tutor ┘  └─ 无候选 → END(学完了)
                                              (回炉巩固)     (真正的结束信号!)

关键改动：2.6 是 plan→quiz（绕过导师），2.7 改成 plan→tutor。讲新课当然先讲课再出题——导师成为所有路径的必经节点，2.6"绕路导致 round 冻结"的死循环隐患从结构上消失。

def plan_node(state):
    conn = init_db(DB_PATH)
    # ① 写回:把这次评估的掌握度存进图谱(地图进度刷新)
    update_mastery(conn, STUDENT, state.get("topic"), state.get("mastery", 0))
    # ② 问图谱:现在"够得着的最差的"是谁?
    nxt = recommend_next(conn, STUDENT)
    conn.close()
    # ③ 决策:有候选 → 推进(换 topic);无候选 → done(真结束)
    if nxt is None:
        return {"action": "done"}
    return {"action": "next", "topic": nxt}

注意：第 ③ 步只动 action 和 topic——topic 换了下一轮导师才讲新课；mastery / round / question 都不能碰。

五、谁在什么时候决定下一个知识点（验收核心）

角色是谁决定什么什么时候起作用
规则你（setup_student 建图）谁有资格当候选（先修门槛）静态，一直存在，不是某个时刻
状态测试（每轮答案→掌握度）学到哪了（进度）运行时不断变化
人选recommend_next 算法够得着的里面具体选谁每次 eval≥0.7 踏进 plan 的那一瞬间
你能定义"游戏规则"（图谱）和"玩家表现"（答案），但"下一步推荐谁"是裁判（算法）在每次回合结束后按规则+表现现判的——你无法钦定，只能影响。改一个答案数字，掌握度变，下次过关后推荐就跟着变——这就是"动态"。

六、测试验收

主场景（真实 LLM，修正答案后）

=== 场景 1: 学二次方程(答对) ===
最终掌握度: 0.7          ← 最后一轮(函数图像)的评估
plan 决策:  done          ← 全学完了!真正的结束信号!
当前知识点: 函数图像      ← 中间发生了 next(二次方程→函数图像)推进
图谱中二次方程掌握度: 1.0 ← 写回成功!

教学宝藏：测试答案笔误 x=0（应为 x=2）→ eval 判 0.4 → 回炉 → 永远 0.4 → round≥10 收工。这不是 bug，恰恰验证了：① should_continue 判定正确；② 保险丝防死循环生效；③ 没到 plan 就不写回，图谱 0.0 未被污染——系统正确识别"没学会"并拒绝推进。

七、本节踩坑清单

#坑表现根治
1概念：以为"路径是测试时写的"复述验收题答偏路径是运行时 recommend_next 现算的；setup_student 只布置棋盘（规则），invoke 只给起点和表现

3state.get("topic") 不给默认值topic 缺失时返回 None 写进库取"必须存在"的字段用 state["topic"]；取"可能没有"的才用 .get(key, 默认值)

遗留问题（2.8 论文系统再解）：quiz_node 沿用外部 question，推进到新知识点后出现"topic=函数图像、考题却是二次方程的题"的错配。真实系统应在 topic 变更时清空 question，或每知识点绑定固定题库。

八、论文定位（答辩话术）

  • 第 5 章核心立论：路径调整是基于知识图谱状态的确定性计算（recommend_next），不是模型随机发挥——可解释、可测试。
  • 创新点表述：不推荐"掌握度最低的"，而是推荐"够得着的最差的"（先修全达标里最弱的）——两关判定 + 边表就是抓手。
  • 对比实验素材：同一份代码改一个答案数字走出两条完全不同的路（答错回炉 vs 答对推进到 done）——动态性的实证。
  • 防死循环方法可写：路径枚举（算法终止性）+ 必经节点计数 + 保险丝，答辩被问"会不会死循环"直接答这套。
