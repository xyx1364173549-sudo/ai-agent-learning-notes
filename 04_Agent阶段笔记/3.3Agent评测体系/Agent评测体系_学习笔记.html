3.3 Agent 评测体系

把"肉眼测"升级成"机器自动打分" → 用数字回答"你的 Agent 到底多好"
评测（evaluation） = 出一张固定卷子 + 机器自动批改 + 算出分数。三个标准动作：① 固定输入（题目写死）② 多轮取平均（跑 N 次）③ 微妙用例（造难判的题）。核心目标是回答：你的 Agent 到底有多好？

一、痛点：手工测试的三个致命伤

手工测试后果
写死 3 个场景，肉眼盯输出不可重复：改一行又得重新肉眼确认
"我感觉还行"没数字：说不出一个百分比
只测了 3 个场景会漏：几十种情况没试

类比：手工测试 = 老师一次出一道题，肉眼看对错（累死）；自动评测 = 出一张卷子，机器批改，算出分数。

二、评测三件套

三件套作用类比
评测集一堆用例，每条 = 固定输入 + 期望结果老师出的卷子
执行器把用例喂给 Agent，拿到实际输出学生做题
打分器对比"期望 vs 实际"，算成功率老师批卷子

关键：评测集题目写死，不靠 LLM 随机出题——评测要"可重复"，随机性会污染结果。

三、两个指标，各考一件事

指标评谁通俗问法
端到端成功率数学辅导 Agent（eval_node）"整张卷子做对几道？"
工具选择准确率天气/计算 Agent（mini_agent）"该用锤子还是扳手，选对几道？"

端到端看结果，工具选择看过程里"选工具"这一步。

四、⭐ 多轮取平均（对抗 LLM 随机性）

LLM 有随机性（temperature 采样），所以单次结果不可信：

跑 1 次 = 得到一个"数字"；跑 N 次 = 得到一个"可信的数字"。前者是彩票，后者是数据。

骰子类比：掷 1 次出 6，不能说"总出 6"；掷 30 次，才能说"概率约 1/6"。

def evaluate(rounds=3):
    rates = []
    for i in range(rounds):
        correct = 0
        for topic, question, answer, expected in CASES:
            if run_case(topic, question, answer) == expected:
                correct += 1
        rates.append(correct / len(CASES))
        print(f"第 {i+1} 轮：{correct}/{len(CASES)}")
    print(f"平均成功率：{sum(rates)/len(rates):.0%}（{rounds} 轮取平均）")

关键认知：跑 N 次不是要改变数字，而是给你"这个数字可不可信"的判断力。判数学对错确定性高（3 轮都满分正常），但"作文好不好"这类主观题随机性大，多轮取平均从"多余"变"必须"。

五、⭐ 微妙用例（别只考"1+1=2"）

满分有两种可能：① 学生真是学霸 ② 卷子只考了"1+1=2"。

你最初的用例全是"非黑即白"，LLM 闭眼满分——测不出真实判断力。要造"难判"的边界用例：

类型例子考什么
漏根x²-4=0 只写 x=2会不会被"部分正确"蒙骗
符号反(x+2)(x+3)（数字对，符号错）会不会被"过程像模像样"蒙骗
方法不同用求根公式而非因式分解，结果对会不会误杀"非标准解法"
过程简略答案对，没写展开过程会不会误杀"过程太短"

工具选择的微妙用例，考的是模糊边界：

用例陷阱考什么
明天适合去爬山吗没提"天气"能不能透过字面看意图
今天出门要带伞吗"带伞"隐含"下雨"能不能做语义联想
北京到上海有多远两个工具都不匹配会不会没工具也硬凑

前两类考"该调时联想到"，后一类考"不该调时忍住"。加进去后成功率会掉，掉下来的那几题，才是你 Agent 真正的短板。

六、⭐ tool_calls 三层嵌套解析

LLM 选工具时返回的 msg 长这样：

msg = {
    "role": "assistant",
    "content": None,              # 调工具时不写正文
    "tool_calls": [               # 第①层：列表（可能调多个工具）
        {
            "id": "call_xxx",
            "function": {         # 第②层：字典（函数信息）
                "name": "get_weather_tool",   # 第③层：字符串（工具名）
                "arguments": '{"city": "北京"}'
            }
        }
    ]
}

为什么三层？ OpenAI 协议：一次回复可能并行调多个工具（最外层用列表）；每个工具调用有一堆属性（用字典）；function 里又有 name/arguments（再套一层字典）。

核心口诀：看它是列表还是字典——遇到列表用 [0] 下标，遇到字典用 ["key"] 键。

所以 tool_calls[0]["function"]["name"] = 「下标 → 键 → 键」交错钻三层。

tool_calls = msg.get("tool_calls")   # 没调工具时拿到 None
if tool_calls:                        # 先确认有包裹，才拆箱
    return tool_calls[0]["function"]["name"]
else:
    return None                       # 闲聊，没调工具
错误写法报错原因
tool_calls["name"]list indices must be integers列表不能用字符串下标
tool_calls[0]["name"]KeyError: 'name'name 藏在 function 里
不判断直接 tool_calls[0]'NoneType' object...没调工具时是 None
