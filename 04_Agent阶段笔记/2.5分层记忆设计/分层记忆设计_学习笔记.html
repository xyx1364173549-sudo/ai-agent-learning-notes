阶段二 · 分层记忆 · 详细版

2.5 分层记忆设计

工作记忆（滑动窗口）+ 情景记忆（SQLite + 遗忘曲线）+ 语义记忆（知识图谱）→ 论文第 4 章创新点基座
三层记忆 = 工作记忆（记得住"刚才说了啥"）+ 情景记忆（记得住"学过什么、忘没忘"）+ 语义记忆（知道"知识间谁先谁后、下一步该学啥"）。三层互补，缺一不可。

〇、为什么不能只有一层记忆？

只有一种记忆会怎样缺了什么
只记对话（工作记忆）重启即失忆，学过的全忘持久化
只存记录（情景记忆）有流水账，但不知道知识点间的先后关系关系结构
只有图谱（语义记忆）知道知识结构，但不知道学生实际掌握多少个人学情

类比：工作记忆 = 黑板（临时写，擦了就没了）；情景记忆 = 笔记本（长期保存，但是流水账）；语义记忆 = 课程大纲（先后顺序，先学啥后学啥）。

三件套的数据流动（答辩会问）

1
工作记忆
对话 → 滑动窗口留最近 N 条 → 发给大模型当上下文
2
情景记忆
学完沉淀 → SQLite 表 → 检索按遗忘曲线加权
3
语义记忆
知识点+先修 → 两张表 → recommend_next 推荐下一步

一、2.5a 工作记忆：滑动窗口

痛点

对话消息无限增长。如果每次都把全部历史发给大模型：

  • token 爆炸 → 费用飙升（LLM 按 token 计费）
  • 上下文被无关历史淹没 → 模型"忘"了当前重点
  • 超过上下文窗口 → 直接报错

方案

只保留两类消息：① system 提示（角色设定，永远不丢）；② 最近的 N 条非 system 消息（N = 窗口大小）。

def sliding_window(messages, max_turns):
    system = [m for m in messages if m["role"] == "system"]
    others = [m for m in messages if m["role"] != "system"]
    others = others[-max_turns:] if max_turns > 0 else []  # 防 [-0:] 返回全列表
    return system + others

边界陷阱（本节第一坑）：others[-0:] 等价于 others[0:]，返回整个列表！因为 -0 就是 0。窗口为 0 = "一条对话都不留"，必须显式钳制：if max_turns > 0 else []。

类比：黑板写满要擦掉旧的。擦 0 行 = 把黑板全擦光，不是"擦 0 行 = 啥也没擦"。

边界测试（跑给你看）

场景输入期望结果
正常max_turns=2system + 最近 2 条✅
窗口为 0max_turns=0只有 system✅（有钳制才对）
负数max_turns=-1保守返回空✅
窗口超大max_turns=100全部非 system 消息✅（切片自动截断）

二、2.5b 情景记忆：SQLite + 遗忘曲线

痛点

  • 要持久化：学过的东西不能只在对话里，程序重启就没了。
  • "学过 ≠ 记住"：时间越久忘得越多，检索要按遗忘程度加权。

SQLite 是文件型数据库——一个 .db 文件就是整个数据库，不需要装服务器，Python 自带 sqlite3 模块，零依赖。

方案 1：episodes 表持久化

CREATE TABLE IF NOT EXISTS episodes (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,  -- 自增主键，每行唯一编号
    student_id TEXT NOT NULL,                      -- 哪个学生
    topic      TEXT NOT NULL,                      -- 学了什么知识点
    summary    TEXT NOT NULL,                      -- 内容摘要
    difficulty REAL NOT NULL,                      -- 难度（0~1）
    score      REAL NOT NULL,                      -- 掌握度得分
    started_at TEXT NOT NULL DEFAULT (datetime('now'))  -- 学习时间（ISO 字符串）
)

为什么 started_at 用 TEXT？ SQLite 没有专门的日期类型，惯例存 ISO 字符串（如 "2026-09-02 21:30:00"），Python 端用 datetime.fromisoformat() 解析。不是 fromtimestamp()——那是给"秒数时间戳"用的，喂 ISO 字符串会类型报错（本节第二坑）。

save_episode：插入 + 拿回主键

def save_episode(conn, student_id, topic, summary, difficulty, score):
    cur = conn.cursor()
    cur.execute("""
        INSERT INTO episodes (student_id, topic, summary, difficulty, score)
        VALUES (?, ?, ?, ?, ?)
    """, (student_id, topic, summary, difficulty, score))
    conn.commit()          # 提交事务，写入才真正落盘
    return cur.lastrowid   # 最后插入行的主键 id

lastrowid 是什么（本节第三坑）：cur.lastrowid = 最后插入那一行的主键 id 值，不是"插了几条"。删掉数据后 id 不回退（AUTOINCREMENT 只增不减）。计数要看 cur.rowcount（受影响条数）或 SELECT COUNT(*)。

踩坑实例：save_episode 签名参数顺序和调用不一致 → 数据静默存反列（topic 和 summary 互换），不报错、查出来才发现。函数参数顺序、SQL 列顺序、调用传参顺序三处必须对齐。

query_episodes：查询 + 排序

def query_episodes(conn, student_id, limit):
    cur = conn.cursor()
    cur.execute("""
        SELECT id, started_at, topic, summary, score
        FROM episodes WHERE student_id = ?
        ORDER BY started_at DESC LIMIT ?
    """, (student_id, limit))
    return cur.fetchall()

注意：ORDER BY started_at DESC 按时间倒序。不写 ORDER BY 永远不要假设返回顺序（下面 2.5c 有 rowid 空洞演示）。

方案 2：艾宾浩斯遗忘曲线加权

原理：记忆随时间指数衰减。距离学习时间越久，检索权重越低。

import math
from datetime import datetime

def days_since(iso_str):
    """ISO 字符串 → 距离今天的天数"""
    dt = datetime.fromisoformat(iso_str)   # ✅ 不是 fromtimestamp！
    return (datetime.now() - dt).days

def decay_weight(days, lam):
    """遗忘曲线权重：w = e^(-λ·days)"""
    return math.exp(-lam * max(days, 0))   # days 取非负，防未来时间算出 >1

math.exp(-x) 是什么：就是 e 的 -x 次幂 e^(-x)。为什么是负数？因为衰减曲线是"时间越久权重越低"——指数上的负号让函数值随 days 增大从 1 单调下降到趋近 0。exp(0)=1（刚学完权重最大），exp(-∞)→0（远古记忆权重趋近 0）。

max(days, 0) 防什么：时间数据出错（如未来时间）时 days 为负，e^(正数)>1 会放大权重。钳到 0 保证权重永远在 (0, 1]。

检索排序：加权分 = 原始分 × 衰减权重

def search_episodes(conn, student_id, limit, lam=0.03):
    cur = conn.cursor()
    cur.execute("""
        SELECT id, started_at, topic, summary, score
        FROM episodes WHERE student_id = ? ORDER BY started_at DESC
    """, (student_id,))
    rows = cur.fetchall()
    scores = []
    for r in rows:                                      # 每一条都要算 → 循环内
        id_, started_at, topic, summary, score = r      # 元组解包：一行拆成 5 个变量
        days = days_since(started_at)
        weight = decay_weight(days, lam)
        scores.append((score * weight, id_, topic, days, weight))  # append 在循环内！
    scores.sort(reverse=True)                           # 全部算完才排一次 → 循环外！
    return scores[:limit]

本节第四坑（缩进）：append 必须在循环内（每一条都要收集）；sort/return 必须在循环外（全部处理完才做一次）。口诀：每一条都要做的 → 循环内；全部完成后再做一次的 → 循环外。

元组解包：id_, started_at, topic, summary, score = r 把一行元组按顺序拆给 5 个变量。变量个数必须和列数一致，多一个少一个都报 ValueError。

λ 翻转实验（论文第 7 章实验素材）

λ 控制遗忘速度：λ 越大忘得越快（更看重近期）；λ 越小越"重实力"（原始得分主导）。

λ二次方程（60天前，原始60）函数图像（38天前，原始38）加权后排序
0.0360 × e^(-1.8) = 60×0.165 ≈ 9.938 × e^(-1.14) = 38×0.319 ≈ 12.1二次方程 ＞ 函数图像
0.0160 × e^(-0.6) = 60×0.549 ≈ 32.938 × e^(-0.38) = 38×0.684 ≈ 26.0函数图像 ＞ 二次方程（翻转！）

同一个数据库、同一个查询，只调 λ 就得到相反的排序结果。说明"遗忘参数"直接决定检索偏好——λ=0.03 优先捞"更久前但更扎实"的记忆，λ=0.01 优先捞"更近期"的记忆。这一张表就能当实验数据。

三、2.5c 语义记忆：知识图谱（两张表）

痛点

情景记忆只能回答"学过什么"，回答不了"接下来该学什么"。因为系统不知道知识点之间的先后关系——先学因式分解才能学二次方程，先学二次方程才能学函数图像。

方案：一张"图" = 两张表

真正的知识图谱通常用图数据库（Neo4j）。我们用 SQLite 降级实现："点"一张表，"边"一张表——避开学图数据库，降低毕设难度，功能照样够。

类比：knowledge 是地铁站（站点 + 人流量），prerequisites 是线路图上的连线（哪站到哪站）。少了任何一张都不成立。

表存什么关键约束类比
knowledge（点）学生 × 知识点 × 掌握度UNIQUE(student_id, topic)地铁站 + 人流量
prerequisites（线）先修关系 from → toPRIMARY KEY(from_topic, to_topic)线路图上的连线

UNIQUE vs PRIMARY KEY：主键一表只能有一个且不能为空；UNIQUE 约束可以有好几个、允许空值。点表用组合 UNIQUE（同学生同知识点唯一），边表用组合主键（同一条边唯一）。这两处约束是 upsert 能工作的前提——没有唯一约束，重复插入不报错，upsert 也没有"冲突"可处理。

写数据：upsert 两兄弟

① ON CONFLICT ... DO UPDATE（点表用，撞了要改）

INSERT INTO knowledge (student_id, topic, mastery) VALUES (?, ?, ?)
ON CONFLICT (student_id, topic)           -- 撞到唯一键了？
DO UPDATE SET mastery = excluded.mastery  -- 用新值把旧掌握度盖掉
  • excluded：SQLite 关键字，指那个想插进来、但被唯一键拦下的新行。excluded.mastery = 新传进来的掌握度
  • 整套动作 = upsert（update + insert）：有就改，没有就加

类比：期末登记成绩单。学号+科目已有一行 → 不新增行，只把分数更新成新成绩；没有 → 新写一行。没有 ON CONFLICT 这句，第二次对同一个 (student_id, topic) 执行 INSERT 会直接抛 IntegrityError: UNIQUE constraint failed。

② INSERT OR IGNORE（边表用，撞了就算了）

INSERT OR IGNORE INTO prerequisites (from_topic, to_topic) VALUES (?, ?)

同样撞主键，态度完全不同：直接跳过，不报错，也不覆盖。"因式分解→二次方程"这条边加两次，语义上就是同一条边，多写没意义。类比：往通讯录加联系人，已经有了就啥也不干。

一句话区分：成绩单撞了要更新（DO UPDATE），关系表撞了就忽略（OR IGNORE）。

读数据：fetch 三形态

方法返回什么没数据时什么时候用
fetchone()单个元组 ("二次方程", 0.6)Noneget_mastery 查单个掌握度
fetchall()元组列表 [("因式分解",0.9), ...][]查一批知识点 / 先修
fetchmany(n)元组列表，最多 n 条[]分页（现在用不到）

关键认知：数据库返回的每一行永远是元组，哪怕只有一个字段。

cur.fetchall()  →  [("因式分解",), ("全等三角形",)]   # 每行是单元素元组
[r[0] for r in ...]  →  ["因式分解", "全等三角形"]      # 剥掉元组壳，只要字符串

为什么数据库给你元组而不是列表？

  • 不可改的快照：给你列表你就能 row[0] = 0.0 手滑改掉，但改的只是 Python 里的拷贝，数据库纹丝不动——产生"我明明改了怎么没变"的错觉。元组想改都改不了，逼你想改必须走 SQL（UPDATE）。
  • 元组可当字典 key：列表可变不能哈希；元组可以。以后写缓存、去重，元组直接塞 set/dict。

r[0] 是列下标，不是行下标（重要认知纠偏）

pres = [r[0] for r in cur.fetchall()]
  • 行下标 = "现在是第几行"——不用你写，for r in rows 每次循环自动换一行
  • 列下标 = "取这一行的第几个字段"——r[0] 固定取第 0 列，不管 r 现在是哪一行

读作："每一行 r，都取它的第 0 列"。三行数据 → 三个 r[0] → 三个字符串。看起来"一样"，是因为语法一样，不是取的同一条。

类比：全班点名，老师喊"报一下你们的学号"——每个被点到的人（r 依次是第 1 个、第 2 个……）报的都是"学号"（第 0 列），你不会觉得老师只问了第一个人。

列数由 SELECT 决定：SELECT topic, mastery → 每行 2 个元素，r[0]=topic、r[1]=mastery；SELECT from_topic → 每行 1 个元素，r[0] 就是唯一元素。跟 WHERE 无关，WHERE 只是筛行，不会加列。

数据库返回顺序不保证（现场演示）

实测：先插甲（rowid=1）、乙（2）、丙（3），删掉乙，再插丁——

第一次查询:  甲(1) 乙(2) 丙(3)     ← 碰巧按插入顺序
删乙、再插丁: 甲(1) 丙(3) 丁(4)     ← 2 号位空了，丁没有补进来

删掉的乙那个位置（2）就空着，新插的丁拿到 rowid=4。数据库只保证每行有唯一编号，不保证返回顺序像数组一样连续。

铁律：不写 ORDER BY，就永远不要假设返回顺序。所以 recommend_next 取"掌握度最低"时要自己 sort：candidates.sort() 之后才是真的"最弱的"。

核心算法：recommend_next 两关判定——"够得着的最差的"

def recommend_next(conn, student_id):
    cur = conn.cursor()
    cur.execute("SELECT topic, mastery FROM knowledge WHERE student_id = ?", (student_id,))
    rows = cur.fetchall()          # ① 先把"所有知识点"端回 Python 存好
    candidates = []                # 空篮子：装"够得着"的候选
    for topic, mastery in rows:
        if mastery >= 0.7:
            continue               # 第一关：已掌握 → 跳过
        # 第二关：查这个知识点的所有先修（查的是边表，跟掌握度无关）
        cur.execute(
            "SELECT from_topic FROM prerequisites WHERE to_topic = ?",
            (topic,),
        )
        pres = [r[0] for r in cur.fetchall()]   # 剥壳：元组列表 → 字符串列表
        ready = True               # 乐观假设：先假设够得着
        for p in pres:             # 逐个先修把关
            if get_mastery(conn, student_id, p) < 0.7:
                ready = False      # 有一个先修没学会 → 否掉
                break
        if ready:                  # 两关都过 → 收进篮子（必须与 for p 平级！）
            candidates.append((mastery, topic))
    if not candidates:
        return None                # 没有候选
    candidates.sort()              # 掌握度升序（弱 → 强）
    return candidates[0][1]        # 返回最弱的那个

三层结构口诀（第四坑的升级版）

1
第 1 层：遍历知识点
每条都要做：判定1 已掌握跳过 → 查先修 → 乐观假设
2
第 2 层：逐个先修把关
一个知识点的先修逐个查，有一个没学会就否掉
3
第 3 层：收尾
全部处理完才排序返回（candidates 空 → None）
  • 每条知识点都要做的 → 第 1 层
  • 一个知识点的先修逐个查 → 第 2 层
  • 全部弄完才做一次 → 第 3 层

踩过的两个具体错法：

  1. for 循环体只剩 continue，后面的 cur.execute 掉到循环外 → 循环空转三圈，topic 残留最后一个值"函数图像"，查出先修"二次方程"掌握度 0.6<0.7 → ready=False → 返回 None。不报错，静默跑错，最阴险。
  2. if ready: 缩进在 for p 里面 → 每个先修达标后都 append 一次。多先修场景下（如"三角函数"依赖"相似三角形"+"全等三角形"）同一个知识点被收集两次。当前数据只有一个先修看不出来，真实图谱里三四个先修是常态——本地全绿、上线才炸。

完整走查（测试数据逐步推演）

知识点表（stu001）：因式分解 0.9 | 二次方程 0.6 | 函数图像 0.3
边表：因式分解 → 二次方程（先学因式分解才能学二次方程）；二次方程 → 函数图像

知识点第一关（掌握≥0.7？）第二关（先修全达标？）结果
因式分解0.9 ≥ 0.7 → 跳过根本没机会查不候选
二次方程0.6 < 0.7 → 过关先修=因式分解 0.9 ≥ 0.7 ✅候选 (0.6, 二次方程)
函数图像0.3 < 0.7 → 过关先修=二次方程 0.6 < 0.7 ❌ → 淘汰不候选

candidates = [(0.6, "二次方程")] → sort → 返回 "二次方程"

为什么不是掌握度最低的"函数图像"（0.3）？因为函数图像的先修"二次方程"只有 0.6 还没学会。硬推函数图像等于把学生往墙上撞——学不会。系统推荐的是"够得着的最差的"：先修全达标里挑掌握度最低的，保证"推了就能学会"。

四、贯穿知识点：SQLite 基础（数据库四件套）

四件套：conn / cursor / execute / fetch

类比：去图书馆查资料。

代码图书馆类比干什么
conn = sqlite3.connect(...)办了张借书证建立到数据库文件的连接通道
cur = conn.cursor()叫了个管理员跑腿真正执行 SQL 的"手"
cur.execute(SQL, 参数)把书单递给管理员让他跑一趟，结果暂时端在手上
cur.fetchall()把书从管理员手里接过来结果拿回 Python，变成列表

游标是"独臂服务员"——一次只能端一盘菜：你 execute 第二次，第一盘结果就被自动收走。所以嵌套查询必须先 fetchall() 固化：

rows = cur.fetchall()   # ← 先把"所有知识点"端走存好
# 之后再 execute 查先修，就不会弄丢 rows

先 fetchall 固化成列表，再进循环——SQL 嵌套查询的通用铁律。不存直接 for t, m in cur: 迭代游标，循环里再次 execute 时外层循环直接乱套。

? 占位符：为什么不用 f-string？

# 千万别这么写（f-string 拼接 SQL）
f"SELECT ... WHERE student_id = '{student_id}'"

# 要这么写（占位符）
cur.execute("SELECT ... WHERE student_id = ?", (student_id,))
  1. 防 SQL 注入：用户输入被当纯数据处理，永远不会被当成 SQL 执行
  2. 自动处理引号转义：中文、标点、引号都不会把 SQL 撑爆
  3. 数据库能缓存执行计划：同一条 SQL 反复执行更快

(student_id,) 尾巴那个逗号不能省

cur.execute("... WHERE student_id = ?", (student_id,))
#                                           ↑ 这个逗号

参数第二项必须是元组。(student_id) 只是加了括号的字符串，不是元组；(student_id,) 才是。单元素元组的逗号是 Python 经典暗坑——和 ("因式分解",) 单列查询结果是同一个规矩。

事务：conn.commit()

SQLite 默认开启事务。execute 只改了内存里的暂存，commit() 才真正写入文件。忘记 commit 的后果：程序正常结束（连接关闭自动回滚），数据"看起来写了"实际没落盘。

进阶（先记着，毕业设计用得上）

conn.row_factory = sqlite3.Row   # 之后 row["topic"] 直接按列名取值

给连接配一个"翻译官"，让每行从元组变成能按列名取的字典式对象，不用记"第 0 列是 topic 还是 mastery"。当前代码用 r[0] 完全没问题，这是"以后让代码更可读"的优化项。
